# Mixed Database Campaign: 2026-10-18

Five bounded Windows runs exercise native relational SQL over disposable KitDB
files, including concurrent managed checkpoints. They measure the current dirty
tree after the KROW scan and snapshot-value optimizations, not a released build.
This work adds a test harness, not production scheduling or storage changes.

All five runs pass their data, index, restart and resource-drain oracles.
**That does not establish a stable release or acceptable production latency.**
The 16-database workload falls short of its requested pacing and has long
checkpoint tails even before a noisy writer is introduced.

## Setup And Scope

- Windows/amd64, Go 1.26.0, GOMAXPROCS=4. Each main case uses a fresh process.
- 1, 4 or 16 resident databases, 1,024 rows/database, a 512-byte tenant-specific
  payload, integer primary key, version and secondary-indexed bucket.
- One point reader and one indexed-page reader per database, each paced at
  10 ms. One normal writer per database, paced at 20 ms, updates one row per
  durable transaction. It updates both version and bucket atomically.
- In noisy mode only database 0 changes: its single writer is unpaced and
  updates 32 rows per transaction. Normal neighbors retain the same pacing,
  payloads, reader counts and transaction sizes. This is more row/index/WAL
  work, not merely a higher number of transactions.
- A shared node manager has up to two maintenance workers (one for the
  one-database case), one outstanding checkpoint per database and a bounded
  queue. Each database requests a checkpoint at 100 ms intervals. Full
  compaction uses the existing manager admission/drain behavior.
- Per database: 256 KiB page-cache ceiling, 8 MiB snapshot admission budget and
  8 MiB transaction budget. Result caching is disabled. Automatic checkpoint
  evaluation is disabled in these attached facades; maintenance is explicit.
- All traffic is in-process SQL. No TCP/pgwire/KitSQL, VM, HTTP, search, KCOL,
  auth/control-panel or host-wide foreground query governor is measured.
- Every case requests eight seconds of work. In-flight operations finish
  before shutdown; throughput uses the actual interval including that drain
  (8.00-8.34 seconds), not setup/reopen/test-process duration.

These are **paced closed-loop workers**, not a fixed-rate open-loop queue.
Missed ticker arrivals are not accumulated. Latency measures actual operations,
including internal waiting but not hypothetical requests that were never sent.
Underload throughput must be considered alongside the percentiles; there is
no coordinated-omission correction or saturation-capacity claim.

Operation durations use Windows QPC. Histograms are bounded and shared with
the existing relational workload tests. p50/p95/p99 below are **bucket upper
bounds**, not exact samples. Maximum latency is recorded separately. Cohorts
merge histogram counts, never average tenant percentiles. Samples below 100
are flagged in JSON; the 1-database checkpoint run has only 80 samples.

The nominal balanced-16 pacing is 1,600 ops/s for each read type and 800
transactions/s. Actual throughput is substantially lower. Noisy aggregate
transaction throughput is not directly comparable to balanced throughput:
database 0 changes 32 rows per commit. At 16 databases there are only 8-16
checkpoint completions per database, so those runs do not reach full compaction.
Full compaction coverage in this campaign comes from the 1/4-database cases.

Rare stalls also matter: noisy-16 maximum point and indexed-page times are
987.2 and 966.6 ms, although their p99 ceilings are 100 and 150 ms. The maximum
checkpoint completion is 2,264.6 ms, versus its 3,000 ms p99 bucket ceiling.
An upper-bound bucket must not be presented as an exact observed latency.

proof for larger fleets, arbitrary traffic or longer periods.

## Memory And Cleanup

Memory is whole test-process memory sampled every 25 ms. Short-lived peaks can
be missed. Cumulative allocation is a separate Go TotalAlloc delta over the
work window, excluding fixture setup and reopen verification, but including
the workload harness and sampler. It is not peak or resident RAM.

| Case | Sampled heap peak MiB | Sampled RSS peak MiB | Allocated during window GiB | Heap after close + GC MiB |
| --- | ---: | ---: | ---: | ---: |
| Balanced 1 | 3.33 | 66.41 | 0.87 | 0.531 |
| Balanced 4 | 8.33 | 28.18 | 3.44 | 0.566 |
| Noisy 4 | 14.13 | 33.47 | 8.94 | 0.568 |
| Balanced 16 | 42.33 | 66.81 | 13.18 | 0.603 |
| Noisy 16 | 45.01 | 68.10 | 12.14 | 0.603 |

The allocation rate is still large despite low retained heap. Different fresh
processes can retain different OS working sets; the one-database RSS peak is
not evidence that opening more databases reduces memory. GC is requested after
close, but memory is not forcibly returned to the OS with FreeOSMemory.

All database snapshot/reservation/waiter/transaction/pending-commit counts and
their tracked bytes are zero after workers finish. After closing the manager,
open database handles, leases, reserved cache, queued/running maintenance are
zero. Every file is then independently reopened, verified and closed. Go
goroutines return from 3 to 3 in every main case.

**OS process handles are not claimed to return to their cold-start count.**
Cold-to-post-close counts increase (for example 133 to 171 in balanced 4).
These include runtime/event/thread handles as well as files; no object-type
classification was performed. A separate two-cycle noisy-4 diagnostic in the
same process observes 141 -> 177 handles in cycle 1, then 177 -> 177 in cycle 2.
Post-close heaps are 587,152 and 601,136 bytes, goroutines are 3 after both, and
all database resources and reopen oracles pass in both cycles. This provides
short-repeat evidence against cumulative growth in that run, not a long-term
leak proof or proof that the initial increase belongs to a particular subsystem.
RSS remains about 67-69 MiB after these cycles and must not be called reclaimed.

## Correctness And Verification

The writer updates its bounded row-version oracle only after commit success.
Commit sync counts must exactly match acknowledged transactions. Concurrent
reads check identity, row consistency, ordering and the tenant-specific payload.
After all writers/checkpoints stop and managed handles close, every row is
checked against the exact last acknowledged version, then all 64 secondary
index buckets are compared against that oracle. Missing, extra, duplicate,
wrong-version and cross-tenant rows fail the run. Kernel Verify also runs on
each independently reopened database. Errors/timeouts are not silently retried.

The harness is opt-in. Normal tests include short one-database/noisy smoke,
configuration bounds, corruption-oracle tests, histogram merging and repeat
bounds. Race checks pass three repetitions. The first exploratory attempt
(`r1`) failed before workload because its one-database configuration requested
two open/maintenance workers; the corrected harness caps workers by database
count and adds that boundary to smoke coverage. It was not an engine failure,
and the failed report is not mixed into the results above.

The production engine was not changed by this campaign. This is not a Windows
release gate, Linux result, physical crash/power-loss drill, 24-hour canary or
qualification of the uncommitted storage optimizations. No commit/push occurred.

Completed verification:

```text
go test ./kitdb/relational -count=1 -timeout=10m
go test -race ./kitdb/relational -run '^TestMixed' -count=3 -timeout=3m
go vet ./kitdb/relational
go build -mod=readonly ./...
```

The full relational suite passed in 158.657 seconds. An initial build exited
successfully but warned that the sandbox could not write Go's module stat
cache; the approved repeat with `GOPROXY=off` and read-only module mode completed
without that warning. No dependencies were downloaded or added. The full engine
UI/browser test suite was not run for this test-only change.

credentials, database import or arbitrary workload SQL.

## Next Decision

The [checkpoint phase follow-up](CHECKPOINT_2026-10-18.md) implements the first
diagnostic step below and records a scoped count optimization, including the
whole-workload regressions and reverse-order repeats rather than only wins.

Measure checkpoint queue time separately from execution, and isolate allocation
profiles for lookup/snapshot/merge/checkpoint work. The current combined
checkpoint timer cannot establish which lock or I/O path caused the tail.
Then compare bounded scheduling/cadence/group-commit changes on the same
workload. Do not increase worker counts or weaken sync/admission simply to
hide the backlog. Longer repeated mixed workloads and deployment-specific
resource envelopes are still needed before production conclusions.
