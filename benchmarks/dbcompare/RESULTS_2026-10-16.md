# Four-Database SQL Comparison: 2026-10-16

Fresh local Windows measurements, not historical values. Every query was checked against the independently generated fixture oracle. These are warm sequential application-facing timings, not a storage-kernel ranking, p99 claim or release qualification.

## Environment and Method

- Windows/amd64; CPU: 11th Gen Intel(R) Core(TM) i7-11850H @ 2.50GHz; one foreground query at a time.
- Engine base commit: `a22edf8d3f677f7006d1bdff3ece61f164e40f8c` with benchmark changes and a dirty workspace. The exact built executable SHA-256 is `820dbe7b05e824473ebf0b3f5f6afe01ccf85f7c97df5e648a17f1feec36ec8e`. No stable/candidate label is inferred.
- Two scales: 100,000 and 1,000,000 rows; seven columns, 64 merchant groups, nullable numeric fields and a repetitive 248-byte payload. Identical generated SQL, integer primary key and `(merchant,id)` index. This is not the 13M production shopping dataset.
- Fresh KitDB schema uses the current exact BIGINT aggregate contract. Historical legacy-integer fixtures are not semantically identical performance baselines; this report does not claim a regression against those older timings.
- Two warmups and seven timed executions per query; median milliseconds below, lower is better. Parse/plan/execute and complete result materialization included. No explicit prepared-statement reuse. Query-result cache is not enabled for KitDB.
- KitDB is standalone `relational.Execute`, not Kitwork ORM/VM. Its row, typed-batch and KCOL profiles share one canonical load. Batch/KCOL paths were asserted, not inferred from a configuration switch.
- SQLite Go uses modernc; SQLite native uses Python stdlib C SQLite with statement caching disabled. DuckDB is native through Python with one thread. Process startup and JSON IPC are excluded from native query timings.
- PostgreSQL is a new disposable portable local server, reached over TCP loopback with lib/pq and one connection. Its timings include protocol and socket overhead; embedded engines do not. It is real PostgreSQL, not KitDB pgwire. The server was stopped after the campaign.
- Durable small-batch ingestion: 128 rows per autocommitted SQL INSERT; explicit checkpoint every 16,384 rows and at completion. SQLite uses WAL/FULL; PostgreSQL uses fsync/full_page_writes/synchronous_commit on; DuckDB persistent defaults; KitDB ordinary synced WAL. Not maximum COPY/appender throughput.
- All profiles ANALYZE after load, timed separately. GOMAXPROCS=1; DuckDB threads=1; PostgreSQL parallel query and JIT off, autovacuum off for the disposable cluster. KitDB/SQLite page caches and PostgreSQL shared_buffers are 64 MiB; PostgreSQL work_mem is 64 MB; DuckDB memory_limit is 512 MB. These are NOT equivalent total-memory caps.
- Fixed engine order on a shared desktop; OS cache and other machine load uncontrolled. No cold-device, native-RSS, concurrent/mixed-load or sustained compaction claim. Seven samples are not sufficient for production percentile claims.

## Interpretation and Limits

- In this campaign, native SQLite had the lowest warm lookup and 100-row-page medians at both scales. Native DuckDB had the lowest full, filtered, NULL-filter and grouped aggregate medians at both scales. This is not a universal database ranking.
- At 1M, KitDB typed KROW full aggregation took 1517.648 ms versus 472.864 ms for native SQLite. KCOL reduced that query to 64.976 ms, still about 4.2 times DuckDB's observed 15.584 ms. GROUP BY through KCOL took 81.331 ms versus DuckDB's 6.669 ms, an observed gap of about 12.2 times.
- KitDB canonical ingestion, including explicit checkpoints, took 146.436 s at 1M versus 24.291 s for native SQLite, 89.463 s for DuckDB and 18.915 s for PostgreSQL over loopback. These are the specified small SQL batches, not optimized bulk loading.
- KitDB KROW/KCOL mode does not accelerate point lookup itself. Differences between their point/range medians must not be attributed to columnar execution: these are separate sequential open/warm series on a shared desktop.
- `COUNT(*)` may use maintained metadata in KitDB: do not interpret it as scanning all rows faster than another engine.
- KCOL query timings exclude its separately recorded build/refresh and history setup costs. A fast KCOL SELECT is not proof of cheap mixed read/write analytics.
- The scalar and typed KROW profiles expose execution overhead rather than hiding it behind the optional columnar projection. Neither should be silently relabeled as the other.
- File lengths and Go cumulative allocation deltas are in raw JSON. They are not native peak RSS or physical disk traffic. PostgreSQL reports only table/TOAST/index relation bytes, not cluster/WAL, so no equal-scope storage ranking is made.
- Only seven fixed SELECT shapes plus one UPDATE/freshness exercise were measured. No general SQL-compatibility, crash durability, cluster, production-readiness or whole-database winner claim follows.
- Initial setup attempt R1 waited for the PostgreSQL process tree in the Windows launcher. It was stopped, produced no campaign timings, and is retained separately. R2 fixed process waiting; workload and benchmark budgets were not relaxed.
