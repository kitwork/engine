# Noisy Sixteen-Database Follow-Up - 2026-10-19

## Decision

Do not make another production-engine change from this evidence. The prior
[SQL ordering correction](SQL_ORDER_2026-10-19.md) remains in place, but its
mixed-workload behavior is not a consistent throughput improvement.

Six new paired repeats have four higher and two lower index rates after the
change. One pair again has a worse after index tail. This does not establish
equivalence, eliminate regressions, or identify the cause of a slow run. It
also does not support treating the previous single noisy-16 regression as a
reliable effect of the planner correction.

Keep cache, worker and memory ceilings and durability unchanged. Read-page
allocation remains the largest measured allocation category. Study that path
with a controlled fixed-work fixture before changing synchronization or
adding another cache. No runtime code, dependency or public API was changed
in this follow-up; these are local diagnostics, not release qualification.

## Repeated Unprofiled Measurements

Exactly the two frozen binaries from the preceding SQL report were used.
Before/after always mean before/after the primary-suffix order correction,
not before/after a new change in this report. Each invocation has fresh
disposable databases in a fresh process. Six pairs alternate execution order,
three before-first and three after-first.

Controls remain eight seconds plus admitted-operation drain, GOMAXPROCS=4,
sixteen databases, 256 KiB page cache and 8 MiB snapshot/write budgets per DB,
at most two managed maintenance workers, and 100 ms explicit checkpoint
cadence. Readers and normal writers are paced at 10/20 ms; database zero has
one unpaced 32-row writer. Result caching and the automatic checkpoint
evaluator are off. No own builds, tests, trace analysis or profiles overlapped
the latency series. Other desktop/OS activity was not controlled or attributed
to a specific process.

The fifteen normal neighbors show paired index-rate changes of -10.2%,
+14.7%, +38.2%, -6.1%, +2.4% and +6.1%, respectively. The variation is not
confined to the noisy database. Before rates span 680.7-1340.9/s and after
rates span 941.9-1382.0/s. Winner counts and these short-run histogram buckets
are not a statistical non-regression gate or a production p99 SLA.

These are paced, closed-loop, time-window workloads. Different progress
changes row versions, overlay size and generation shape, even with identical
inputs and limits. Therefore neither total bytes allocated nor rates from
separate windows are a fixed-work per-operation comparison. No claim is made
that external scheduling, GC or any particular host process caused a slow pair.

Maintenance scheduler-wait p99 buckets range from 500 to 1,500 ms before and
500 to 1,000 ms after; service p99 ranges from 100 to 500 ms before and 100 to
250 ms after. These are separate distributions, not components that may be
added to recover the p99 of one checkpoint. Service includes locks, file work,
handle acquisition and sync; the timestamp resolution is coarser than the
enclosing QPC operation timer.

## Separate Workload-Window Profiles

CPU and allocation modes run separately on each frozen binary, after fixture
creation and through admitted-operation drain, before verification/reopen.
Allocation analysis subtracts the pre-window cumulative heap profile. The
window includes GC, maintenance, memory sampling and harness activity, not
just query goroutines. Profiled latency is excluded from the table above.

| Allocation attribution | Before sampled share | After sampled share |
| --- | ---: | ---: |
| Page read plus mutation-page decode, cumulative | 77.19% | 79.60% |
| Snapshot overlay map clone, flat | 4.13% | 3.31% |
| Projected KROW decoder, cumulative | 1.69% | 1.46% |
| Secondary-index collection, cumulative | 2.02% | 1.71% |

The page category includes other nested categories, so shares must not be
added indiscriminately. Sampled window totals are about 9,426 MiB before and
9,090 MiB after, with different operation counts: this is not a matched
allocation-reduction ratio. Query `readMatchingRows` owns much of the sampled
page allocation, but includes its nested cursor and point-fetch work.

Windows CPU profiles have substantial native/syscall attribution under
`runtime.cgocall` (about 55% flat in the after window). That is not proof of
pure computation, physical disk latency or a new C database dependency. The
reported total CPU sample duration can exceed GOMAXPROCS times wall time when
native/syscall threads are attributed this way; do not turn it into a CPU
utilization claim. GC and allocation work are also visible, but are not a
disjoint wall-clock explanation for the paired latency variation.

An additional after-only diagnostic build with `kitdb_profile` records named
checkpoint/storage trace regions and synchronization/scheduler profiles.
This instrumented build is not a third latency candidate and is not a tagged
before/after comparison. The validated trace contains 279 checkpoint
executions: 278 incremental append publications and one no-op. It records no
snapshot-drain/full-compaction region in this short window; that is not a
claim that compaction is free or absent under sustained operation.

Two workers overlap, so summed execution is about sixteen seconds during an
8.189-second workload/drain. Nested regions overlap their parents and sync
regions overlap append/rotation. Never add these percentiles or region totals
as if they were disjoint elapsed time. In this trace, reopening a generation
and rotating the WAL are larger checkpoint regions than counting records;
changing the already-optimized count again would not target its largest
remaining measured component. Those region durations include waits and file
operations, not just CPU or device fsync. Directory-sync call duration on
Windows may be a platform no-op and does not prove cross-platform durability.

The synchronization profile has about 516 summed goroutine-seconds of waiting:
56.47% is attributed flat to select, 20.02% to channel receive and 12.68% to
Mutex.Lock. It includes normal pacing, ticket waits and idle commit-writer
channels, not just contention. The runnable-scheduler profile similarly sums
goroutine delays, not CPU utilization. These after-only profiles show where
waiting exists; without a matched before trace and lock-specific comparison
they do not establish a new global-lock regression from the planner change.

## Correctness And Scope

The twelve unprofiled reports acknowledge 65,973 transactions. The five
profiled reports acknowledge another 29,397 transactions; keep those cohorts
separate for performance conclusions. All seventeen reports passed exact
row/version/payload and secondary-index verification after independently
reopening every database, per-tenant ACK/sync equality and owned-resource
drain checks. Managers closed with zero owned handles, leases and pending
maintenance work. Derived validation and file hashes are retained locally.

The trace summarizer tests passed (1.116s), as did the profile harness
exclusive-file/lifecycle tests and mixed smoke (3.623s). The real trace was
parsed with matched named regions; synchronization/scheduler profiles were
extracted as binary streams, not text-redirection conversions.

This follow-up does not rerun a clean-candidate release campaign or establish
Linux, networked KitSQL/pgwire, long-duration fairness, physical power-loss safety, process
OS-handle reclamation or production stability. Earlier engine gates apply to
the unchanged code evidenced in the previous report, not to an invented new
release. No commit or push was made.

## Next Controlled Experiment

Use a fixed transaction/query count and seeded schedule, reporting per-operation
page reads and decode allocation, rather than comparing unequal progress in
another short timed window. Candidate work is bounded reader-buffer reuse
without changing caller-owned result bytes or adding a new retained cache.
Separately investigate generation-open/WAL-rotation phases only with their
existing crash/publication gates: never remove sync, weaken checksum checks
or increase workers to conceal a slow region. These are investigation targets,
not changes implemented or claimed faster by this report.
