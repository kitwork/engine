# SQL Primary-Suffix Ordering - 2026-10-19

## Finding And Change

This follows [bounded range reads](RANGE_BOUNDS_2026-10-18.md). Profiling the
unchanged native relational index query found repeated page reads/decodes as
the dominant allocation source, rather than SQL parsing. Existing secondary
keys already append the ordered primary tuple, but the planner only checked
declared index fields for ORDER BY coverage.

The planner now recognizes that physical suffix. With primary key id and an
index on bucket, `WHERE bucket=4 ORDER BY id LIMIT 16` no longer hydrates the
whole matching prefix and maintains an in-memory Top-N heap. It walks the
existing index order and stops after sixteen matching rows. Residual filters
and OFFSET are still evaluated before deciding to stop.

The runtime change is confined to `relational/index.go`: pass the already
resolved primary fields into order matching, append missing primary members
to a private effective-order slice, then use the existing coverage checks.
Primary members already declared in the index are redundant within their
earlier groups and do not get counted twice. No persisted key, index readiness
rule, public API, row codec, cache setting, worker count, or WAL policy changed.
There is no new primary-suffix range pushdown or general cost-based optimizer.

## Profile Evidence

The fixture is the existing BenchmarkReadPaths setup: 1,024 rows with 512-byte
payloads, an index on bucket, a primary key on id, seventeen checkpointed
generations, 256 KiB page cache and 8 MiB snapshot/write budgets. The measured
query selects id, version, bucket and payload for bucket 4, ordered by id with
LIMIT 16. Query-result caching is off. There is no pgwire, ORM, VM or network
in this path.

A separate four-second benchmark profile before the change reports sampled
allocation of about 7,385 MiB including benchmark setup/calibration. Its cumulative
allocation attribution is approximately:

- Main page reading and mutation-page decode: 85.3%.
- Point fetches inside index hydration: 57.7% (overlaps the page category).
- Initial index cursor construction: 31.6% (also overlaps page work).
- Projected KROW decode: 4.6%.

These are sampled allocation shares, not wall-time shares or disjoint phases.
The process-wide CPU profile includes fixture preparation and GC. It is useful
for locating code paths, not for assigning exact query-only CPU percentages.
Profiled benchmark latency is excluded from the unprofiled comparison below.

The fixture has forty matching rows by its independent version model. The
old uncovered-order executor uses Top-N over the matching prefix. The new
evidence test checks the exact first sixteen rows against that model and
asserts sixteen index entries, point fetches and hydrated rows via EXPLAIN
ANALYZE. Skipping hydration avoids more work than merely decoding fewer
projected fields. It is not an index-only SELECT: returned rows still come
from canonical KROW in one fixed snapshot.

The separate instrumented run, after validating the ordinary result, reports
16 point lookups and 16 hydrated rows, but still 17 page reads / 133,776 page
bytes from eager segment initialization. Early row stop is not zero prefetch,
and this warmed diagnostic is not a cold-cache I/O measurement.

## Unprofiled Before And After

Both frozen binaries contain the earlier kernel/read-path optimizations. The
BenchmarkReadPaths body and fixture are unchanged. Each ordering runs five
repetitions with 200 fixed iterations and CPU=4 on the same Windows desktop.
The first sweep runs all four benchmark cases before then after; the second
runs the index case after then before, in separate fresh processes.

| Index measurement | Before | After |
| --- | ---: | ---: |
| First sweep median | 878 us/op | 371 us/op |
| First sweep range | 799-1,091 us/op | 337-421 us/op |
| After-first sweep median | 695 us/op | 330 us/op |
| After-first sweep range | 645-760 us/op | 312-344 us/op |
| Allocated bytes/op | about 774,000 | about 306,250 |
| Allocations/op | 1,070-1,071 | 585-586 |

Allocation drops about 60%, and the measured median latency drops about
53-58% in these two short sweeps. This is a workload-specific improvement,
not a claim that all SQL is twice as fast. Metadata (240 B/op, six objects),
kernel point reads (576 B/op, one object), and SQL point reads (about 21 KB,
143 objects) retain their allocation envelopes. OS cache, thermals and other
desktop processes are uncontrolled; no own build/test/profile overlapped
these latency measurements.

## Correctness And Gates

New tests cover primary suffixes, repeated/reordered primary members, composite
keys, signed IDs, fixed and varying preceding fields, ascending/reverse and
mixed-direction fallback. A seeded 500-shape soundness test checks planner
claims against sorted actual ordered-scalar key bytes and independently
compares the resulting requested row order.

The SQL integration test uses an independent in-memory row model across WAL,
checkpoint, retained snapshots, index mutations, reopen, own transaction
writes and rollback. It checks residual predicates and OFFSET before early
stop. Streaming tests compare exact results with materialized execution for
forward, reverse, residual, no-LIMIT and LIMIT-zero shapes, and require mixed
directions to retain their materialization fallback.
