# Windows WAL Publication Failure Phases

## Result

A new diagnostic build reproduced the real refusal at **`replace-target`**:
the native `SetFileInformationByHandle` call returned Windows errno 5 with
`published=false`. Opening the publication handle had succeeded. The native
unsupported-API fallback and the post-publication flush were not reached.

This identifies the failing operation, not the OS handle, filter driver or
policy causing the refusal. Publication availability remains unresolved.
No retry, sharing bypass, security exclusion or replacement algorithm change
was introduced. The withdrawn secondary-copy experiment remains withdrawn;
no A/A or A/B performance campaign was restarted.

## Implementation

The Windows publisher now returns phase-aware errors while retaining the
original native cause and `os.LinkError` for `errors.Is/As`. Labels distinguish
source resolution/opening, native target replacement, unsupported fallback,
post-rename sync and source-handle close. The existing `published` boolean and
`ErrDurabilityUncertain` continue controlling recovery. Failure after rename
must not restore the old WAL's offsets onto a replacement.

`kitdb/internal/waldiag` has an ordinary no-op implementation and a separate
`windows && kitdb_waldiag` implementation. The ordinary observer does not read
environment variables, inspect metadata or call Restart Manager; its zero-allocation
behavior is tested. Successful publication never invokes failure observation.
The diagnostic build requires an explicit plain fixture root with a host-created
marker and an absolute, fresh report outside that root. It reads the small marker,
not WAL/database contents. Paths must remain beneath the configured root.

Capture executes in the publisher's error branch, before its cleanup defers,
staging-writer removal and old-WAL restoration. It records metadata for both
paths, the current-process publication handle's identity when available, and
bounded Restart Manager resource users (three list attempts, at most 256 users).
The first exclusive report reservation wins; subsequent failures do not overwrite
it. No mutable global callback, observer registry or foreign-handle access is
installed. These are trusted test-build controls, not app/tenant capabilities.

Capture is not atomic with the failed OS call. Metadata errors must not be read
as proof of absence; resource users do not reveal blocking share flags. Native
queries are synchronous and can perturb a failing workload. Diagnostic timing
therefore cannot be substituted for ordinary-build performance evidence.

## Controlled Evidence

Real no-delete-share file handles independently force:

| Control | Required phase | Native rename calls | Publication result |
| --- | --- | ---: | --- |
| Hold staging source | `open-source` | 0 | Refused, both file contents unchanged |
| Hold target WAL | `replace-target` | 1 | Refused, both file contents unchanged |
| Unsupported-native test control + held target | `fallback-replace` | 1 native callback | Legacy refusal remains visible |
| Tagged post-rename sync failure | `sync-published` | Native rename succeeds | Published, durability uncertain, fail closed |

The tagged observer controls verify that both paths still exist at pre-rename
refusal, that the publication handle is still open during target-refusal capture,
and that a known current-process resource user is observed. Post-rename sync
capture instead requires the staging name absent, target present and publication
handle still open. The report cannot be overwritten by a second controlled error.

Existing history-on/off, compact/incremental, ACK recovery and hard-exit tests
remain in place. The sync test now additionally requires the exact phase.
The first smoke test used `File.Stat` as a closed-handle oracle; Windows reported
an invalid native handle rather than `os.ErrClosed`. That test-only oracle was
corrected to the existing `File.Write(nil)` closed-file contract; no publication
handle leak was established by that initial assertion.

## Real Workload Observation

A fresh tagged binary was built from a captured 630-file scoped corpus and ran
the existing bounded native-SQL forensic campaign on generated OS-temp data.
It failed during its first warmup after 21.84 seconds (whole test duration),
rather than completing its planned 2+8 thirty-second windows. No failed
checkpoint was retried and no missing window was counted as passing.

The capture for database 12, before publisher cleanup, records:

| Field | Observation |
| --- | --- |
| Phase | `replace-target` |
| Windows errno | 5, access denied |
| Published flag | false |
| Source | Exists, 64 bytes, native attributes 32 |
| Target | Exists, 3,872 bytes, native attributes 32 |
| Read-only attribute | Not set on either observed path |
| Publication handle | Present/open, with volume/file identity |
| Resource users | Current forensic test process only |

The publication handle refers to the staging source. Seeing this process in
the combined source/target resource-user query does **not** prove it owns a
blocking target handle. An empty/non-exhaustive external-user list likewise
does not exclude a transient/kernel user. Earlier post-cleanup observations
that also listed `System` remain separate evidence; neither observation
identifies the refusing handle or justifies disabling a security component.

All owners subsequently closed with zero leases, cache reservations, queued or
running maintenance. The failed maintenance operation remained recorded as a
failure. Recovery opened only verified copies: all 16 databases matched the
independent model for **16,013 acknowledged transactions**. Original digests
were unchanged. Both the original and verified-copy fixtures were additionally
preserved in the workspace (96 files with SHA-256 checks); OS-temp originals
were not deleted.

This is bounded recovery evidence, not a successful campaign, physical-disk or
power-loss evidence, or a stable-release qualification.

## Verification

The Windows lifecycle normal/race gate now selects both `kitdb/relational` and
`kitdb` and requires both native denial phases plus resolution/fallback refusal
classification. Each step has 17 required PASS entries; package omissions,
missing/failed/skipped required cases are rejected. Non-Windows plans retain
their existing eight requirements rather than counting Windows skips as evidence.

| Scope | Root passes | Root skips |
| --- | ---: | ---: |
| Focused ordinary WAL checks | 11 | 0 |
| Focused race WAL checks | 11 | 0 |
| Tagged diagnostic race checks | 2 | 0 |
| Combined diagnostic/fault matrix | 15 | 1 child-only skip |
| Broad KitDB + releasegate | 959 | 20 |

The broad suite passes 15 packages. Ordinary and diagnostic-tag vet/build pass.
These are KitDB-scoped checks, not a full-engine `go test ./...` run. Local
evidence lives in `.artifacts/kitdb-wal-phase-20261026/`, including source/binary
manifests, pre-cleanup JSON, failed forensic output, independent ACK verification,
preserved fixtures, test JSON and lifecycle gate evidence. See
[`kitdb/FAULT_LAB.md`](../../kitdb/FAULT_LAB.md#windows-wal-publication-diagnostics)
for build-tag and fresh-fixture instructions.

Next investigation should identify source-versus-target users/owned handles at
the native refusal boundary without inferring share flags from a PID list. A
real publication fix must preserve fail-closed post-rename behavior and then
earn a fresh Windows qualification and A/A + A/B run. This work does not install
drivers, change permissions/power/security settings, create services, commit or
push, or qualify Linux/mobile/cold OS cache/long-duration production operation.
