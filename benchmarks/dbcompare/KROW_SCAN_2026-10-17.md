# Reusable KROW Scan: 2026-10-17

This follow-up reduces allocation in the authoritative row-store scan used by
typed relational batches. It does not change KROW/KCOL/WAL formats, commit
validation, fsync policy, snapshot capture, SQL syntax, or projection freshness.
It does not replace the storage engine or claim production readiness.

## Change And Ownership

`Snapshot.Scan` visits read-only key/value slices which are valid only during
the callback. A caller retaining data must copy it. Forward scans own one
reusable checked page per immutable source segment and reusable merge-output
buffers. Output is preserved before advancing a source that can overwrite its
page. Reverse scans use the existing reader. There is no global pool, unsafe
aliasing, whole-result cache or dependency addition.

The typed KROW batch decoder now consumes these borrowed rows directly.
Ordinary `Cursor.Key`/`Value` still return caller-owned copies; point lookup,
index cursors, scalar execution and KCOL execution are not rewritten. Existing
batch eligibility/options remain unchanged. Scratch memory depends on segment
count and page/row bounds, not just a single fixed buffer; this is not a new
whole-process memory ceiling.

The initial allocation profile identified page-buffer/row decoding and
`Cursor.Value` cloning as dominant costs. A separate after-profile shows that
they no longer dominate the cumulative allocation profile. That profile also
contains fixture-reference generation and database open; it is not itself a
per-query memory measurement. Timed results below do not enable profiling.

## Method

- Windows/amd64, Go 1.26.0, GOMAXPROCS=1, configured 64 MiB page cache.
- Existing deterministic 1,000,000-row fixture, including its completed
  midpoint UPDATE (`-updated`). No ingestion, DDL, DML, index rebuild or KCOL
  refresh. Normal open/close housekeeping is allowed.
- Two warmups and seven samples per query; SQL parsing/planning/execution and
  result materialization included. Allocation is a separate `TotalAlloc` delta
  execution after timing, not live/peak RSS.
- Sequential runs: original A, optimized A, original B, optimized B. Test/build
  work was not run concurrently with these timed processes. OS cache, CPU power
  state and other desktop activity were not controlled.
- Every query matches the independently regenerated fixture oracle. The runner
  requires the requested `krow-batch`/`kcol-batch` path rather than hiding fallback.

## Measurements

All latencies are medians in milliseconds. Both repeats are retained.

| Query | Original A | Optimized A | Original B | Optimized B | Allocated bytes original A | Allocated bytes optimized A |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Full aggregate | 1058.4403 | 620.1033 | 1602.7118 | 801.3155 | 769,191,312 | 8,486,144 |
| Filtered aggregate | 1014.4648 | 760.8540 | 1430.8978 | 787.1137 | 769,208,056 | 8,503,024 |
| Group by merchant | 1032.1462 | 780.6078 | 1441.0011 | 806.2626 | 769,224,736 | 8,514,968 |

The allocation reduction is approximately **98.9%** on these three queries.
The two optimized allocation samples are identical; original repeat differences
are under 1 KiB. This is lower cumulative allocation, not a claim that resident
RAM fell from 769 MB to 8.5 MB.

Observed latency falls by about 24-50% across the paired runs. Machine noise
is substantial: original full-aggregate medians differ by about 51% between A
and B. Therefore no fixed speedup, p99 improvement or cross-database ranking is
claimed. See the raw samples rather than treating these medians as an SLA.

The unchanged point-lookup control allocates 26,664 bytes in all four runs;
its medians vary from 0.0726 to 0.2777 ms. The unchanged indexed-page path
allocates 824,856-824,952 bytes; medians vary from 1.4101 to 2.6922 ms.
These controls expose timing variability and are not optimization claims.

An optimized-binary KCOL correctness/path control returns exact answers using
`kcol-batch`: full aggregate 47.1685 ms / 132,776 allocated bytes, filtered
aggregate 51.8147 ms / 159,224 bytes, grouping 64.4046 ms / 165,896 bytes.
There is no paired original KCOL timing here, so this is not a KCOL speedup or
formal non-regression claim.

## Correctness And Verification

`kitdb/scan_rows_test.go` covers forward/reverse ranges, limits, empty ranges,
multiple pages and generations, WAL overlay updates/deletes, legacy files,
snapshot visibility after commit/checkpoint, callback errors/early stop, close
inside a callback, concurrent close, and corrupt first/subsequent pages.

The 2,048-row allocation envelope permits at most 100 allocations. The measured
non-race run uses 18; final race runs use 21-22. This test excludes snapshot
creation and does not guarantee constant memory for arbitrary segment counts.

Completed checks:

```text
go test ./kitdb/... -count=1 -timeout=10m
go test -race ./kitdb ./kitdb/relational -run '^(TestSnapshotScan|TestBatchGroup|TestAnalyticsDictionaryText|TestSnapshotAdmission)' -count=3 -timeout=5m
go test -race ./kitdb -run '^TestSnapshotScan' -count=3 -v -timeout=5m
go vet ./kitdb/... ./benchmarks/dbcompare
go build ./...
go test ./benchmarks/dbcompare -count=1
go test ./work -run '^TestKitDBDatabaseReleaseGate$' -count=1 -v -timeout=5m
```

The full KitDB suite and relational race run preceded the final test-only
addition for corruption on the second page; that addition passed the final
scan race run. Production Go source was unchanged between those checks.
Whole-engine tests and release qualification are not implied by a successful
whole-engine build. Earlier candidate qualification does not qualify this
uncommitted optimization.

A broader `go test ./benchmarks/dbcompare ./work -run 'Test|^TestKitDBDatabaseReleaseGate$'
-count=1 -timeout=5m` passed the benchmark package, but the `work` package reached
its global five-minute timeout with `TestBrowserScrolledFollowsThePage` active
for 11 seconds. This does not prove that individual browser test was hung or
that KROW caused a regression. The broad run is **not passing evidence** and
was not repaired or given a larger budget here. The isolated database gate
subsequently passed in 1.70 seconds (5.293 seconds package time). Its six stages
cover schema/CRUD/transactions/indexes, source reopen, verification, backup,
restore and restored-query verification.

## Next Boundary

This completes a measured scan-allocation improvement, not the entire KitDB
optimization roadmap. Write/checkpoint costs, snapshot-overlay copying,
common SQL/ORM execution, multi-tenant fairness and KCOL freshness remain
separate work. A later batch should profile one of those paths with its own
correctness and durability gates, rather than combining a storage redesign
with this change. No Linux run, 24-hour canary, commit or push was performed.

In the separate optimized CPU profile, generation merge still accounts for
54.78% cumulative samples and batch decoding for 33.76% (overlapping call
trees, not additive percentages). These are concrete next profiling targets;
they are not evidence that checksum validation should be removed. Windows
`runtime.cgocall` includes operating-system calls and does not imply this scan
delegates storage to another database engine.
