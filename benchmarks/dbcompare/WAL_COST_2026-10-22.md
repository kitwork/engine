# Windows WAL Publication Cost, 2026-10-22

## Decision

Keep the compatible-reader fix as a scoped **development candidate**, with a
small measured allocation cost. Do not promote it to a stable release or call
the 16-database latency budget cleared. The fixed checkpoint benchmark did not
show a latency regression in these four pairs, but the SQL load has substantial
timing variation and worse checkpoint samples after the change at 16 databases.
The separate repeated-owner diagnostics also retain their process-growth review
flags on both sides; OS-handle/thread behavior is not cleared.

This follows the [publication correctness report](WAL_PUBLICATION_2026-10-22.md).
It does not identify the owner of the older spontaneous Windows denial. The
compatibility regression and fault/crash evidence remain separate from these
performance observations.

## Sources And Method

Windows/amd64, Go 1.26.0, Intel i7-11850H, GOMAXPROCS=4. Two fresh local clones
use commit `4d36264cbd102a162f1b54908df29f53b422080e` and the same prior 14-file
overlay. Complete source inventories prove that only these four paths differ:

- `kitdb/wal.go`
- `kitdb/storage_io.go`
- `kitdb/publish_wal_windows.go` (new)
- `kitdb/publish_wal_other.go` (new; inactive on Windows)

Both sides retain identical projection, page representation, SQL, test bodies,
dependencies and durability settings. Unrelated shared-tree compiler/UI/HTTP
work is excluded. All four test binaries were built offline before measurement.
No own build or profiling ran concurrently with the timed windows.

One retained checkpoint warmup pair is excluded. Four measured pairs alternate
after/before, before/after, after/before, before/after. Each side runs the fixed
checkpoint benchmark followed by balanced SQL windows at 1, 4 and 16 databases.
There are four independent samples per side/configuration, not four independent
machines. OS caching, background activity, thermal state and storage-controller
behavior are not controlled; this is not a confidence interval or capacity SLA.

No production code or test threshold changed during this campaign. Retained
history is **off** in these performance fixtures; history-on correctness is
covered by the earlier tests, not a history-on performance measurement here.

## Fixed Checkpoint Work

The existing `BenchmarkCheckpointOverlay128` starts with 8,192 rows of 512-byte
values and checkpoints 128 updates per iteration. Updates are outside the
benchmark timer and allocation accounting. Each measured sample has exactly
32 timed checkpoints (128 per side overall); compaction is left enabled.
Go's separate calibration invocation is not one of those measured samples.
The benchmark verifies the resulting database. It uses real synced WAL I/O,
not a mocked Sync, and measures the whole checkpoint, not just rename/flush.

| Metric | Before | After |
| --- | ---: | ---: |
| Median of sample-average checkpoint time | 18.902 ms | 17.204 ms |
| Sample-average time range | 15.572-36.025 ms | 15.360-24.134 ms |
| Median allocated bytes/checkpoint | 422,407.5 | 422,770 |
| Allocations/checkpoint, every sample | 1,106 | 1,109 |

The paired byte deltas are +289, +427, +424 and +303 bytes/checkpoint. The
allocation delta is exactly **+3 in every pair**. The difference between byte
medians is about +0.086%; it is cumulative Go allocation, not resident memory.
The added source handle is closed; allocation counts do not count OS handles.

Paired timing changes are -5.68%, -11.53%, -33.01% and -1.36%. Despite their
direction, the wide baseline range prevents a general speedup claim. Neither
the extra Sync cost nor the rename cost is isolated by this end-to-end test.

## Mixed Native SQL

The unchanged `TestKitDBMixedCampaign` runs 24 fresh-process windows, each
requesting 10 seconds plus admitted-operation drain. Every database has 1,024
rows, 512-byte payloads, one point reader and one index reader paced at 10 ms,
a single-row writer at 20 ms, and managed checkpoint requests at 100 ms.
The manager has at most two maintenance workers. Query-result caching is off;
page cache is 256 KiB/database and snapshot/transaction budgets are 8 MiB each.
This is paced closed-loop load, **not maximum throughput**.

Both sides have identical queries, fixtures, pacing and duration, but completed
operation counts differ. They are not claimed to have executed identical fixed
SQL operation counts. Counts below are medians over four windows; latency
columns are medians of histogram bucket upper bounds, not exact quantiles.
In particular, a median of window p95 bounds is not a pooled global p95.

| Databases | ACK commits before/after | Checkpoint calls before/after | Checkpoint p50 bound before/after | Checkpoint p95 bound before/after |
| --- | ---: | ---: | ---: | ---: |
| 1 | 500 / 497 | 101 / 101 | 50 / 50 ms | 50 / 50 ms |
| 4 | 1,954 / 1,978.5 | 398.5 / 402.5 | 50 / 50 ms | 100 / 100 ms |
| 16 | 7,493.5 / 7,457 | 626.5 / 583 | 275 / 350 ms | 525 / 625 ms |

At 16 databases, checkpoint p95 bounds range from 300 to 750 ms before and
300 to 1,000 ms after. Calls include scheduler queueing, acquisition and reader
drain, not only WAL publication. A regression at this scale is **not ruled out**;
queue/service attribution and fixed-work saturation measurements are the next
performance investigation. Do not infer an acceptable tail from the smaller
fixed benchmark. Raw reports retain all histograms, including p99; this report
does not establish a production tail guarantee from four short windows.

All windows pass the unchanged per-commit Sync, row/index oracle, close/reopen
and resource-drain checks. Before: 39,745 ACK commits, 153,346 point/index reads,
4,418 checkpoint calls (4,399 advancing publication). After: 39,417 ACK commits,
150,507 point/index reads, 4,316 checkpoint calls (4,299 advancing publication).
These counts exclude fixture seeding and reopen verification.

| Databases | Median cumulative allocation before/after | Median sampled peak heap before/after | Median sampled peak RSS before/after |
| --- | ---: | ---: | ---: |
| 1 | 917.8 / 911.9 MB | 2.94 / 3.15 MB | 20.94 / 20.91 MB |
| 4 | 3,552.4 / 3,563.5 MB | 8.68 / 8.09 MB | 28.97 / 28.52 MB |
| 16 | 12,815.4 / 12,556.5 MB | 31.19 / 31.44 MB | 57.06 / 57.03 MB |

MB means decimal 1,000,000 bytes. Allocation is process TotalAlloc over a
window, not peak or retained RAM; different completed work prevents calling its
decrease a memory optimization. Heap/RSS peaks are 25 ms samples and may miss
short peaks. The 1-database RSS ranges reach about 70 MB on both sides, so the
median alone does not describe the full memory variability.

## Resource Ownership

All 24 managers close with zero managed/open/opening/closing databases, leases,
waiters, reserved cache bytes and queued/running maintenance. Kernel snapshots,
reservations, waiters, transactions, transaction bytes and pending commits drain
to zero; reopened databases preserve the independent row/index oracle. Every
fresh-process window returns to its starting goroutine count.

Total process handles do **not** return to the pre-open baseline: deltas span
+18..+104 before and +18..+144 after. These are whole-process observations, not
counts of KitDB-owned file handles. Node counters alone cannot prove that every
OS handle was released. A separate repeated-owner lifecycle diagnostic is
recorded below; it is not included in the latency comparison.

The existing `TestKitDBLifecycleCampaign` then runs serially on each binary:
ten 2-second windows in the same process, 16 databases/window, alternating
balanced/noisy load, two warmups and eight measured owner lifetimes. Both runs
pass correctness and verify all 160 database reopen lifetimes per side. They
retain the full window JSONL, per-round OS thread counts and warmup/final
goroutine/heap profiles. These additional windows are not part of the 24 timed
SQL windows.

| Post-warmup observation | Before | After |
| --- | ---: | ---: |
| Process handle range | 224-230 | 212-236 |
| Process handle first-to-last change | +6 | +24 |
| OS thread range | 19-20 | 17-21 |
| Goroutines after close/GC, every measured window | 2 | 2 |
| `process_growth_review_required` | true | true |

Neither handle nor thread tail is exactly flat. Thread variation and the
baseline's own growth are relevant observations, **not proof that Go owns every
remaining handle** or that KitDB leaks none. Do not waive these flags or rerun
until a flat tail appears. No growing KitDB lease/queue/database counters or
lost ACK was observed; whole-process ownership attribution remains open.

## Reproduction And Evidence

Build from the two recorded sources first, then run their binaries serially:

```powershell
go test -c -o kernel.test.exe ./kitdb
go test -c -o relational.test.exe ./kitdb/relational
./kernel.test.exe -test.run='^$' -test.bench='^BenchmarkCheckpointOverlay128$' -test.benchtime=32x -test.count=1 -test.benchmem

$env:KITDB_MIXED_CAMPAIGN='1'
$env:KITDB_MIXED_SECONDS='10'
$env:KITDB_MIXED_REPEATS='1'
$env:KITDB_MIXED_REPORT='<fresh report path>'
./relational.test.exe -test.run='^TestKitDBMixedCampaign$/^balanced_16$' -test.count=1 -test.v
```

Use the campaign's GOMAXPROCS=4/offline environment and fresh reports; repeat
for balanced_1 and balanced_4 and alternate the two binaries as recorded. Do
not run the new compatible-reader regression against the old implementation
as though its expected failure were a performance sample.

Local evidence: `.artifacts/kitdb-wal-cost-20261022/`. It retains source
inventories, preparation/runner/analysis scripts, all 38 step logs, ten raw
checkpoint samples (two warmup samples excluded), 24 complete mixed reports,
compiled binaries, and the assessment. Test-owned temporary databases are
removed by the existing tests; these are not retained forensic fixtures.

The scoped candidate links back to the exact source and full correctness
evidence of the preceding publication campaign. It is not a qualification of
the changing shared checkout. No Linux run, physical power cut, 24-hour soak,
