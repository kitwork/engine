# Private Page-Row Positions: Windows, 2026-10-22

## Change

Decoded page rows now store three positions and a deletion flag instead of two
byte-slice headers and a deletion flag. `rowPage` still owns the complete data
buffer; row views are constructed from validated positions when needed.

This is private in-memory metadata, not a new disk format, SQL API, index,
cache, or pool. Both legacy row pages and mutation pages still validate every
record, ordering, trailing bytes, checksum, and directory fences. Public Get
and cursor results keep their existing caller-owned copies. The conservative
48-byte per-row cache admission charge is unchanged, so the experiment does
not increase the admitted page count to obtain better hit rates.

## Allocation Results

Six unprofiled samples per implementation and case, reported as medians:

| Case | Before B/op | After B/op | Allocated-byte reduction |
| --- | ---: | ---: | ---: |
| Decode one 128-row page | 8,256 | 4,160 | 49.61% |
| Read/checksum/decode page | 65,611 | 61,515 | 6.24% |
| Read/checksum/decode, reused buffers | 0 | 0 | Unchanged |
| Native SQL point | 41,029 | 40,193.5 | 2.04% |
| Native SQL index | 534,195 | 487,228.5 | 8.79% |
| Native SQL scan | 2,297,605.5 | 2,278,756.5 | 0.82% |

Decode still allocates two objects; fresh read/checksum/decode still allocates
three. SQL point remains at 144 allocs/op, scan at 17,209. Index medians are
507/506, but this small adaptive-run variation does not establish a generally
removed allocation. The page metadata arrays are smaller, not fewer. Go
allocation size-class rounding contributes to the 4,096-byte page saving.
Allocated bytes are not peak memory or retained heap measurements.

## Method

- Windows/amd64, Intel i7-11850H, Go 1.26.0, GOMAXPROCS 4.
- New `BenchmarkPageReadPhases` separates warm OS-cache file reads, CRC32C,
  fresh decode, fresh read/checksum/decode, and reused read/checksum/decode.
  Every phase uses the same 51,328-byte, 128-record mutation page with 384-byte
  values. This is not cold-device I/O. Phase medians must not be subtracted to
  manufacture a SQL materialization cost; they are separate workloads.
- Existing unchanged `BenchmarkFixedReadWork` supplies integrated native SQL
  point/index/scan measurements: 1,024 rows, 512-byte payloads, 16 deterministic
  32-row updates, 17 generations, 256 KiB page cache, 8 MiB snapshot/write budgets.
  SQL parsing, binding, projection and independent result validation are inside
  the measured loop. Result caching is off; measured queries do not write.
- Paired order is before/after/after/before. Each process uses three repeats,
  four CPUs, 1 second per phase sample or 2 seconds per SQL sample. Adaptive Go
  iteration counts are used, not the older 128-operation diagnostic schedule.
  No own build/test/profile process overlaps these final benchmark runs.

## Verification

- New page-position, corruption and ownership tests passed three repeats.
  Coverage includes both page formats, 128 rows, large/empty values, tombstones,
  metadata-buffer reuse, 30 malformed-page/checksum/fence scenarios, validation
  of a bad later row during point lookup, forward/reverse cursor retention,
  cache enabled/disabled, snapshot isolation across checkpoint, and closed reads.
- `go test ./kitdb/...`: 879 root test/fuzz-seed passes across 13 tested packages.
  Fifteen opt-in/helper tests and two packages with no tests are skipped; see
  the exact list in local `assessment.json`. This is not an all-engine test run.
- Focused kernel race suite: 60 root passes, no skips. This is not a full-suite
  race run. `go vet ./kitdb/...` passed.
- `go build ./...` passed for the frozen after-source engine on Windows.
- Dedicated lifecycle gate passed normal and race steps, each with all 11
  required Windows entries and no skips, in 45.3 seconds.
- Existing row-page and mutation-page decoder fuzz targets each passed a
  10-second campaign: 380,439 and 402,930 executions. These fuzz targets exercise
  parser/decoder acceptance; the new row views are checked by deterministic tests.

## Provenance And Limits

Local evidence lives in `.artifacts/kitdb-page-rows-20261022/`: separate before
and after source clones/manifests, binary hashes, raw tests/fuzz/gate output,
96 raw benchmark samples, execution records, and `assessment.json`.

Both snapshots start at local candidate
`3ae270052df8a3a347f811599a24f677d0bf8b00`. The before manifest freezes 23 scoped
files, including the prior SQL-capacity/timer-test changes and the new phase
benchmark. After changes five private storage source files and adds one test
file, with all 24 files hashed. The manifests, not the candidate commit alone,
define the tested dirty snapshots. No unrelated UI/JIT work was included.

No new commit, push, Linux test, 24-hour canary, full release gate, cross-database
comparison, or stability promotion was made. The earlier unresolved Windows
WAL-publication failure is not erased by these passing tests. The large raw-page
buffer allocation, snapshot setup, SQL materialization, and I/O remain separate
optimization targets. The prior iteration is recorded in
[SQL source-row capacity](SELECT_CAPACITY_2026-10-21.md).
