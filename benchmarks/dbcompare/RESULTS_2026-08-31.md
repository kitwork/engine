# Standalone SQL Results: 2026-08-31

Measured locally, not extrapolated. These are workload results, not a database
ranking or release-readiness claim. Production files and the existing 13M-row
shopping database were not opened or modified.

These are the original pre-optimization measurements. A later
[index-range follow-up](INDEX_RANGE_2026-08-31.md) fixes the bounded page
bottleneck identified here; the original table is preserved as baseline evidence.
The subsequent [grouped batch follow-up](GROUP_BATCH_2026-08-31.md) addresses the
integer-key GROUP BY fallback without changing these original observations.

## Environment

- Windows/amd64, Intel Core i7-11850H, Go 1.26.0.
- Standalone KitDB `relational.Execute`, not Kitwork ORM/VM or a server protocol.
- SQLite 3.53.1 through modernc v1.51.0 and Python's native SQLite 3.53.1.
- DuckDB 1.5.0 through an isolated Python wheel; Python 3.12.13.
- One sequential query at a time; `GOMAXPROCS=1`, DuckDB `threads=1`.
- KitDB/SQLite page caches configured to 64 MiB; DuckDB memory limit 512 MB.
  These are different kinds of controls, not equivalent process-memory limits.
- Two warmups, seven samples, median below. All query results checked against
  the independent fixture reference, including NULLs and post-update totals.
- Same seven-column SQL fixture, integer PK and `(merchant,id)` index. Descriptions
  are 248 bytes and mostly repetitive. Not a realistic compression distribution.
- QPC timing on Windows; no claim of cold OS cache or isolated desktop load.

Command, from the engine directory:

## Aggregate Scaling

Query:

```sql
SELECT COUNT(*), COUNT(price), SUM(price), AVG(rating), MIN(price), MAX(rating)
FROM products;
```

All times in milliseconds:

| Profile | 10,000 rows | 100,000 rows | 1,000,000 rows |
| --- | ---: | ---: | ---: |
| KitDB KROW scalar | 29.158 | 420.808 | 3474.944 |
| KitDB KROW batch | 14.479 | 83.722 | 1066.114 |
| KitDB KCOL | 0.434 | 3.375 | 39.169 |
| SQLite Go | 2.336 | 27.629 | 510.860 |
| SQLite native | 1.096 | 15.790 | 369.611 |
| DuckDB | 0.460 | 3.035 | 14.065 |

At 1M, KCOL is about 89x faster than KitDB's scalar path and 27x faster
than its KROW batch path for this query. DuckDB is about 2.8x faster than KCOL.
Near-equality at 10k/100k must not be extrapolated to larger datasets.

| SQLite native | 0.009 | 0.155 | 0.137 | 306.609 | 3766.490 |
| DuckDB | 0.374 | 1.054 | 0.355 | 9.877 | 5.917 |

Indexed page:

```sql
SELECT id, name, price, merchant
FROM products
WHERE merchant = 7 AND id >= 500000
ORDER BY id
LIMIT 100;
```

KitDB's EXPLAIN reports `products_merchant_id`, `index scan`, `order=index`.
The index exists and is selected, but that does not guarantee cheap execution.
This query allocated approximately **252.6 MB cumulatively per execution** in
all three KitDB profiles despite returning just 100 rows. It is a high-priority
profiling target, not evidence that another storage format is required.

Filtered aggregate:

```sql
SELECT COUNT(*), SUM(price), AVG(rating)
FROM products
WHERE price >= 2500 AND price < 7500 AND enabled = true;
```

GROUP BY:

```sql
SELECT merchant, COUNT(*), SUM(price)
FROM products
GROUP BY merchant
ORDER BY merchant;
```

KitDB's KCOL option does **not** accelerate this GROUP BY: it falls back to
the scalar path. DuckDB completes it in about 5.9 ms versus KitDB's 3.4 seconds.
`COUNT(*)` is different again: KitDB can answer from maintained row-count metadata,
so its tiny latency must not be advertised as a million-row scan time.

## Ingestion Cost

Seconds, including explicit checkpoints but excluding fixture generation and
schema creation. The three KitDB profiles share one canonical ingestion.
Every 128-row INSERT commits durably; explicit checkpoint every 16,384 rows.

| Engine | 10k rows | 100k rows | 1M rows | Checkpoint portion at 1M |
| --- | ---: | ---: | ---: | ---: |
| KitDB | 0.537 | 9.898 | 135.193 | 20.114 |
| SQLite Go | 0.137 | 1.626 | 21.922 | 1.748 |
| SQLite native | 0.090 | 1.443 | 18.678 | 1.626 |
| DuckDB | 0.618 | 7.690 | 83.688 | 5.478 |

These are small-batch SQL timings, **not maximum bulk-import throughput**.
DuckDB COPY/appender, larger transactions and alternate checkpoint policies
have not been measured. KitDB ingestion also needs work; the fast KCOL read
path does not make its canonical write path faster.

## Columnar Lifecycle At 1M

| Operation | Time | Evidence |
| --- | ---: | --- |
| Open and enable retained history | 5091.31 ms | Separate from initial KCOL build |
| Initial KCOL build | 1372.75 ms | 1M rows, 123 chunks, about 45.05 MB file |
| One durable UPDATE | 7.30 ms | Price at midpoint changed to 99999 |
| Aggregate before refresh | 1163.33 ms | Correct latest total, `krow-batch` fallback |
| Refresh after UPDATE | 96.34 ms | Rebuild 8192 rows; reuse 991808 rows |
| Unchanged refresh | 84.09 ms | Zero bytes written, verification still costs time |
| Aggregate after refresh | 35.83 ms | Correct latest total, `kcol-batch` |

Refresh after UPDATE appended 390,808 bytes, copied zero old payload bytes and
referenced 44,658,492 existing bytes. That is useful write savings, but not a
zero-cost refresh. The stale-snapshot fallback is correct and costly: one row
change temporarily sends this aggregate back to a full KROW batch scan.

One-shot update/refresh timings above are diagnostics, not p95/p99 estimates.

## Storage And Allocation

Decimal MB, file lengths at the recorded observation point, not peak disk usage:

| Profile/component at 1M | MB |
| --- | ---: |
| KitDB canonical database, including indexes | 535.86 |
| KCOL after the one-row refresh | 45.44 |
| Retained-history base snapshot | 535.82 |
| KitDB + KCOL + enabled history, total files | 1117.13 |
| SQLite Go, database + WAL/shared-memory files | 308.99 |
| SQLite native, database + WAL/shared-memory files | 308.99 |
| DuckDB, database + WAL | 87.31 |

**Do not report KCOL's 45 MB as KitDB's total database size.** Enabling retained
history in this experiment creates a full base snapshot, approximately doubling
the canonical storage before counting KCOL. That base belongs to retained
history, not to the KCOL format itself. Making projection history needs cheaper
or more explicit is a separate engineering question.

An extra Go allocation sample for the full aggregate recorded:

| KitDB path | Cumulative allocated bytes per query |
| --- | ---: |
| KROW scalar | 3,828,388,216 |
| KROW batch | 1,185,167,296 |
| KCOL | 134,936 |

These are cumulative allocations, **not resident memory or peak RAM**. Native
allocations were not measured, so this is not a memory ranking against DuckDB
or native SQLite. The KROW batch path is not zero-allocation today.

## Engineering Conclusions

1. The optional KCOL path has real value for its supported ungrouped aggregates;
   this experiment does not justify rewriting canonical KROW/WAL.
2. Profile bounded secondary-index pages first. Returning 100 rows must not
   routinely allocate hundreds of MB as the database grows.
3. Implement/test grouped batch execution before describing KitDB as a general
   analytical engine. Current GROUP BY does not benefit from KCOL.
4. Measure and reduce canonical scan/ingestion allocations and checkpoint costs.
5. Keep the correctness-first stale fallback, but investigate snapshot-aware
   selective refresh/delta execution separately. Do not hide its current latency.
6. Retained history's base snapshot is a real storage/setup cost and should be
   explicit in any operational projection policy.

All 18 profile/scale reports completed without a query-result mismatch. This
does not test crash/power-loss safety, 13M real rows, FTS, PostgreSQL/Turso,
partitions, joins, multi-tenant concurrency or mixed read/write load. Those need
separate, reproducible campaigns rather than extrapolation from these numbers.
