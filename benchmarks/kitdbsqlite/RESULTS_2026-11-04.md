# Anchors of the History on the Shopping File: 2026-11-04

Evidence for `docs/KITWORK_KITDB.md` mục 5 of the Kitwork repository: what an anchor costs on a file the size of
`shopping`, as written today against one that keeps only the pages changed since the anchor before it. One Windows
machine, NVMe, 32 GB RAM, one run of `kitdbsqlite anchor` on a copy of `.database/shopping/kitwork.db`. Not a
production latency claim.

## The file

1,684,128 pages of 16 KiB (25.70 GB), 13,773,074 rows of `shopping`, a STRICT rowid table with
`PRIMARY KEY (merchant, id)`.

| Reading or copying the whole file | Time |
|---|---|
| every page read from the file | 15.77 s (1.63 GB/s) |
| every page read through `sqlite_dbpage`, one read transaction | 39.65 s |
| a byte copy of the file | 70.04 s |
| today's anchor (`VACUUM INTO`, the history cut to its last commit, `VACUUM`) | 433.39 s, 25.66 GB |

Today's anchor writes the file about three times: `VACUUM INTO`, then `VACUUM` of the copy, which SQLite writes
to a temporary file and back.

## Between two anchors

Writes go through the engine's writer (`kitdb/sqlite`), one request each from sixteen goroutines, so the history
grows as an app's would. After each step the file is checkpointed, every page is hashed, and the pages that differ
from the step before are written as a delta: each page's number and bytes.

| Step | Writes/s | Pages changed | Delta | Pages by owner |
|---|---:|---:|---:|---|
| 1,000 updates of random rows | 1,374 | 1,232 | 19.3 MB | shopping 1,001, kitwork_history 230 |
| 10,000 updates of random rows | 1,610 | 12,366 | 193.3 MB | shopping 9,971, kitwork_history 2,394 |
| 100,000 updates of random rows | 1,847 | 121,071 | 1.85 GB | shopping 96,634, kitwork_history 24,436 |
| 100,000 updates on 10,000 hot rows | 1,799 | 34,341 | 536.7 MB | kitwork_history 24,356, shopping 9,984 |
| 100,000 inserts | 1,512 | 25,497 | 398.5 MB | kitwork_history 13,168, shopping 12,164, index 164 |

Each step also changed page 1 (`sqlite_schema`, the header). The history after the five steps: 38,884 commits,
917.8 MB of changes for 311,000 writes, about 2.95 KB a change. Hashing every page took 16 to 18 s a step; writing
the largest delta took 13.88 s.

On a file this size a scattered update changes a page of its own: 16 KiB in the delta, against about 3 KB of
history. A hot set of rows, or inserts, changes far fewer pages; then the history is most of the delta.

## Restoring the last commit

| Restore | Time |
|---|---|
| today: copy the anchor, replay the 38,884 commits since it | 131.38 s |
| by pages: copy the base, write the five deltas | 52.17 s + 9.48 s |

Both read `{rows 13873074, stock -212487, sold 1312863953, ids 278133657622330691, last row 13873074, revision 38884}`,
the file's own; the pages restored are the file byte for byte (every page's hash).

## Kept on disk

Today: one whole copy a day of commits, 25.66 GB each, up to `days + 1` of them (about 795 GB for the default 30
days). By pages: the base, 25.70 GB, and the five deltas, 2.97 GB together.

# at() Going Backward on the Shopping File: 2026-11-04

Evidence for the "hướng lùi" of `docs/KITWORK_KITDB.md` mục 5: `kitdbsqlite at` on another copy of
`.database/shopping/kitwork.db`, same machine. Backward, a read at a past revision r runs in one read transaction
of the live file: the commits after r are read, and every row they changed is put back as it was at r (the Before of
its first change after r; no row when that change inserted it) in two temporary tables of the connection
(`temp_store` in memory); the statement reads the live rows the history after r did not touch together with those.
Today `at()` restores the file as it was at r (the anchor, then every commit up to r) into a copy and reads it.

The workload, through the engine's writer after Open wrote its anchor (330.77 s): 300,000 writes in random order
(150,000 updates of random rows, 100,000 on 10,000 hot rows, 30,000 inserts, 20,000 deletes), 1,711 writes/s,
37,483 commits, 299,721 row changes, 1,015,989,396 bytes of history (3,390 bytes a change).

# SQLite Changesets as the History's Format: 2026-11-04

seed: 150,000 random updates, 100,000 on 10,000 hot rows, 30,000 inserts, 20,000 deletes) on two more copies of

interface translated to Go (`modernc.org/sqlite/lib`), WAL, `synchronous=FULL`. On one copy a session records
`shopping` for each commit and its changeset is taken; on the other no session runs.

# History Format 3 on the Shopping File: 2026-11-04

The writer writes history format 3 since engine 12da2d74 (`docs/KITWORK_KITDB.md` mục 5): an update keeps the columns
it changed, each with its old and new value; inserts and deletes keep their whole image. `kitdbsqlite at` ran again,
the same writes (atWorkload, the same seed), on a fresh copy of `.database/shopping/kitwork.db`, modernc.org/sqlite
v1.51.0. Going backward now rebuilds the rows with `kitdb.WholeImages`, as the engine's at() does: an update's row as
it was is the live row, read by rowid, with the old values of every change after the moment set.

| | Format 1 | Format 3 |
|---|---:|---:|
| `kitwork_history` for the 300,000 writes | 1,015,989,396 bytes (3,390 a write) | 107,358,418 bytes (358 a write) |
| Writes/s through the writer | 1,711 | 1,845 |
| Open writing its anchor | 330.77 s | 285.25 s |

| Changes after r | Rows | Setup, format 1 (history + overlay) | Setup, format 3 | Read by key | Page of 50 | Today (restore) | Same rows |
|---:|---:|---:|---:|---:|---:|---:|---|
| 1,004 | 994 | 36 ms | 73 ms | 0.13 ms | 0.18 ms | 122.14 s | yes |
| 10,001 | 9,503 | 0.27 s | 1.17 s | 0.11 ms | 0.21 ms | 124.54 s | yes |
| 100,008 | 76,160 | 3.90 s | 13.18 s | 0.12 ms | 0.21 ms | 100.62 s | yes |
| 299,723 | 208,806 | 9.45 s | 25.59 s | 0.24 ms | 0.49 ms | 71.58 s | yes |

- The history is 9.5 times smaller and the writes a little faster; restoring replays a ninth of the bytes.
- Going backward reads, besides the history, every changed row that still exists, by rowid: random reads of the
  25.70 GB file, which make the setup slower than format 1's for many changes (on the 30,000-row file of the dry run,
  in cache, it was faster). It stays 3 to 100 times faster than the restore. A view that joins the live row to the old
  values of its changed columns, read only for the rows a statement touches, would remove those reads.
- Every read gave the same rows as on the restored copy, so format 3 restores and goes backward correctly on the
  shopping rows.

# at() Going Backward Reads No Row Ahead: 2026-11-04

`kitdb.PastRelation` (engine 5f283b8d) builds the table as it was from the history alone: a changed row's columns take
the old value of the first change after the moment that touched them; a row deleted since is whole from the history; a
row still there is read through the view, the table LEFT JOIN the old values of its changed columns, only the columns
some update touched going through a CASE cast to their declared type. Format 3 before it read every changed row still
there by rowid while building. `kitdbsqlite at` now reads through `PastRelation` itself, the engine's at(); a fresh
copy of shopping, modernc v1.61.1, the same writes.

| Changes after r | Rows | Setup, format 1 | Setup, format 3 reading rows ahead | Setup, PastRelation | Read by key | Page of 50 | Count of lazada | Same rows |
|---:|---:|---:|---:|---:|---:|---:|---:|---|
| 1,008 | 998 | 36 ms | 73–98 ms | 11.21 ms | 0.12 ms | 0.20 ms | 134.29 ms | yes |
| 10,010 | 9,512 | 0.27 s | 1.17 s | 104.91 ms | 0.16 ms | 0.27 ms | 257.39 ms | yes |
| 100,002 | 76,155 | 3.90 s | 11.06–13.18 s | 550.28 ms | 0.08 ms | 0.18 ms | 149.47 ms | yes |
| 299,721 | 208,806 | 9.45 s | 25.59–32.81 s | 1.38 s | 0.13 ms | 0.18 ms | 174.21 ms | yes |

- Through the view a read by key still uses the primary key and a page in id order still merges both sides: the key
  columns are never patched, so they read straight from the table. The count reads every lazada row through the join.
- The same run gave 1,409 writes/s and Open's anchor in 387.77 s, against 1,828 and 293.81 s the run before: the
  writes do not reach the new code; the machine was busier.
