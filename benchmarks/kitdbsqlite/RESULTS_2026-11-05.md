# The Engine's Page Anchors on the Shopping File: 2026-11-05

Evidence for `docs/KITWORK_KITDB.md` mục 5 and câu 13.9 of the Kitwork repository: the anchors `kitdb/sqlite` writes
since 05/11/2026, measured on the file the 04/11 run measured
(`RESULTS_2026-11-04.md`, "Anchors of the History on the Shopping File"). One Windows machine, NVMe, 32 GB RAM, one
run of `kitdbsqlite anchor` on a copy of `.database/shopping/kitwork.db`. Not a production latency claim.

## The file

1,684,128 pages of 16 KiB (25.70 GB), 13,773,074 rows of `shopping`, history format 3.

## What an anchor is now

- The first anchor of a file is a base, `<rev>-<at>.base`: every page of the file at that revision, read through
  `sqlite_dbpage` in one read transaction of its own while the writer goes on, copied byte for byte. It is a SQLite
  file.
- Every later anchor is a `<rev>-<at>.pages`: only the pages that changed since the anchor before it, found by
  comparing a SHA-256 (16 bytes) of each page with `pages.hashes`, the hashes of the newest anchor. Its header names
  the revision it is taken against; a SHA-256 of the whole file closes it.
- A restore copies the base, writes each `.pages` of the chain in order, cuts the file to the last one's page count,
  then replays the history after the anchor.
- Retain keeps the newest anchor at or before `now - days`. When that is a `.pages`, its chain is written into the
  base, which takes its name, and the `.pages` written go.

## Anchors between steps of writes

Writes go through the engine's writer, one request each from sixteen goroutines. After each step one anchor.

| Step | Writes/s | Anchor | `.pages` |
|---|---:|---:|---:|
| the first anchor, a base (`Open`) | | 84.90 s | 25.70 GB |
| 1,000 updates of random rows | 1,446 | 56.95 s | 15.8 MB |
| 10,000 updates of random rows | 1,549 | 58.11 s | 156.5 MB |
| 100,000 updates of random rows | 1,736 | 60.63 s | 1.48 GB |
| 100,000 updates on 10,000 hot rows | 2,123 | 53.65 s | 162.4 MB |
| 100,000 inserts | 1,721 | 59.56 s | 398.2 MB |

`pages.hashes` is 25.7 MB. An anchor's time is reading every page through `sqlite_dbpage` (39.65 s alone on 04/11)
and hashing it, whatever changed; the `.pages` written is what changed. Against the 04/11 run's deltas of the same
steps (19.3 MB, 193.3 MB, 1.85 GB, 536.7 MB, 398.5 MB, history format 1), the history's pages are fewer with format 3:
the hot rows' step is 162.4 MB against 536.7 MB.

After the five steps, the anchors are 27.92 GB: the base and 2.2 GB of `.pages`. The anchor written until 04/11 was a
whole copy each time, 433.39 s and 25.66 GB, so six of them would be about 154 GB.

## Restores and the fold

| | Time | Rows |
|---|---:|---|
| restore at the second anchor (base + 2 `.pages`) | 52.00 s | the same as the file then |
| restore at the last anchor (base + 5 `.pages`) | 61.32 s | the same as the file then |
| Retain a day after the third anchor, a day kept: three `.pages` written into the base, the history before let go | 9.80 s | |
| restore at the third anchor (the folded base) | 50.57 s | the same as the file then |
| restore at the last anchor (folded base + 2 `.pages`) | 43.85 s | the same as the file then |

"The same" compares the rows' count, the sums of `stock`, `sold` and `id`, the last rowid and the last revision of
the restored file with those of the file at the anchor's revision. On 04/11 a restore from the whole copy took
131 s. After the fold the anchors are 26.28 GB: the base at revision 13,887 and the two `.pages` after it.

## What it costs

- Disk: one base the size of the file, then the pages changed each day, instead of a whole copy each day
  (`days + 1` copies).
- Time: an anchor reads the whole file once (about a minute here), on a read connection: the writer is held only for
  an anchor written at a Barrier, as before (433 s before).
- The history kept in an anchor: a base is the file as it was, its `kitwork_history` with it, so a change's images
  can stay on disk about `2 × days` (decided 05/11/2026, câu 13.9).

# Reads Right After a Commit: 2026-11-05

Evidence for `docs/KITWORK_KITDB.md` mục 10 ("Còn mở từ bản thử": a rare slow read of 15-80 ms right after a commit,
its root not known) and mục 11, step 3. `kitdbsqlite readtail` on a file of 100,000 rows: four writers commit one-row
updates through the engine's writer without pause while four readers read one row at a time as `Database.Read` does
(a read transaction on a pool of read-only connections, the revision it sees, the row), each read's time split into
its steps. 20 s a run; the same machine as above, four sets of runs.

| Runs | Reads | Reads of 10 ms or more | The slowest |
|---|---:|---:|---:|
| writers, Windows' timer as it is (9 runs) | 6,126,000 | 23 (3.8 a million) | 86.69 ms |
| writers, timer at 1 ms by `timeBeginPeriod` (6 runs) | 4,035,000 | 20 (5.0 a million) | 85.35 ms |
| no writer (3 runs) | 2,744,000 | 2 (0.7 a million) | 12.53 ms |
| plain Go, a SHA-256 of 4 KiB a step, writers committing (2 runs) | 28,557,000 steps | 0 | 2.27 ms |
| a shared lock on one byte of a file, taken and given back (`LockFileEx`, `UnlockFileEx`), no writer | 14,972,000 | 0 (14 of 2 ms or more) | 8.51 ms |

- The slow reads come and go: a run has none, a few, sixteen at most. Most wait at the start of the read
  transaction (its first statement), some in `BEGIN`, in the row's read or in the rollback, with or without writers.
- Windows' timer is not the root: at 1 ms they stay. SQLite's WAL reader does sleep between retries, but a sleep there
  would not survive a 1 ms timer.
- Go is not the root: plain Go work beside the same writers never stopped 10 ms.
- What a read does that plain Go does not is call Windows: a lock on the `-shm` and the database file at the start and
  the end of every read transaction, and a read of the file for a page not in the connection's cache. The locks alone
  stopped for up to 8.51 ms, not 10: that is the likeliest place of the tail, not a proof; the file reads were not
  measured alone. The 15-80 ms of the 26/10 prototype was on a machine about half as fast that day.
- The reads of about a millisecond (6-9 % of reads, the p99 of every run) are the clock, not a wait: Go's clock on this
  machine moves in steps of about 0.5 ms, so a read crossing one is counted as one; they are as many with no writer
  and in the rollback, which touches no page.
- Not measured: Linux, where these calls are other ones (no Linux on this machine).

# KCOL on SQLite: 2026-11-05

Evidence for `docs/KITWORK_KITDB.md` mục 6, 7 and 11 (bước 2) of the Kitwork repository: the column copy of
`kitdb/analytics`, built from `.database/shopping/kitwork.db` opened read-only (13,773,074 rows), answering the
analytic queries of `RESULTS_2026-10-27.md`. The copy answers every query twice first, the second timed, then SQLite
answers each: a SQLite scan of the whole file pushes the copy out of the system's file cache, so alternating would
time the copy read from disk.

The copy of eleven columns (`merchant`, `id`, `shop`, `category`, `price`, `pricing`, `discount`, `sold`, `stock`,
`review`, `official`) builds in 49-65 s and weighs 1.33 GB (`kitdbsqlite analytics`).

| Query | The copy, read directly | The copy, through the port | SQLite through the port | Result |
|---|---:|---:|---:|---|
| common category + SUM/AVG | 0.68 s | 0.87 s | 25.77 s | the same |
| rare category + SUM/AVG/MAX | 0.90 s | 0.98 s | 27.64 s | the same |
| high id range + SUM/AVG | 0.40 s | 0.46 s | 12.03 s | the same |
| GROUP BY category (5,699 groups) | 1.42 s | 1.38 s | 44.85 s | the same |
| GROUP BY merchant, count only | 1.10 s | 1.05 s | 5.45 s | the same |
| GROUP BY merchant + SUM(price) | 1.43 s | 1.27 s | 40.89 s | the same |
| whole table: COUNT, SUM, MIN, MAX | 0.13 s | 0.10 s | 30.71 s | the same |

"Through the port" is `kitdbsqlite port`: two sessions of `kitdb/gateway` on the file, one with a registry finding the
copy, one without; the statements are the SQL of 27/10 as a PostgreSQL client sends them, and the results are compared
field for field, column names and types included. The machine ran SQLite about 1.4 times slower than on 27/10 (the
common category took 18.7-21.5 s then); the copy of KROW's day answered the same queries in 0.22-0.81 s.

How the port chose its path: SQLite's plan scanning the table (plain, or through an index for its order: `GROUP BY
merchant` goes through the key `(merchant, id)` and took 35 s on SQLite before the rule took it) goes to the copy; a
plan searching an index runs on SQLite for 100 ms first (the high id range is a skip-scan over the key's second column,
10-12 s on SQLite), and the copy answers what SQLite does not finish within it.
