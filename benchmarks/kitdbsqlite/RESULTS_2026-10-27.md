# KitDB and SQLite on the Retained Shopping Table: 2026-10-27

Evidence for the KitDB-on-SQLite direction (Kitwork repository, `docs/KITWORK_KITDB.md`): SQLite keeps the rows,
KitDB keeps the writer, history, KCOL, search and sync above them. One Windows machine, one Go process per run,
warm best of up to three runs. Not a production latency claim.

## Data

- KitDB source: the retained `shopping` table, 13,773,074 rows, 31 fields, `data.kitdb` 30,054,427,583 bytes.
  Every run opened a copy; the source file, its `.search` and `.wal` were not opened.
- SQLite target: `main.db`, a STRICT rowid table with `PRIMARY KEY (merchant, id)`, 16 KiB pages, WAL,
  27,592,671,232 bytes, written by `kitdbsqlite copy` in 16 min 8 s (about 15,000 rows/s).
- Per merchant: lazada 109,430, shopee 11,023,195, tiki 2,640,449.
- Page size trial, bytes per row: 4 KiB 1,695, 8 KiB 1,593, 16 KiB 1,469, 32 KiB 1,414.

## Identity

- `copy` and `verify` chain the PostgreSQL import's row checksum over the KitDB stream and over the SQLite
  read-back in `(merchant, id)` order. Both are
  `61f81d185299a5ffc8dbabaab7c6e1c8b4cbc3951b59a4671fc8b38606b327b7`; zero rows were out of order;
  `PRAGMA quick_check` is `ok`. JSON fields were byte-identical to KitDB's on a 240,000-row sample.
- The chain does not reproduce the import's own checksum (`632c9b16…`, 2026-08-28): KitDB normalizes decimals
  on write (`4.50` becomes `4.5`, `0.00` becomes `0`), per value. KitDB against the original PostgreSQL rows is
  therefore not verified by this run.

## Setup

- 32 GB RAM with about 17 GB free, smaller than either file; both files on NVMe.
- KitDB: `relational.OpenWithOptions` with `ExperimentalProjections` and `BatchAggregates`; point and page
  queries through `ExecutePlan` (parsed once), analytics through `Execute`.
- SQLite: modernc.org/sqlite v1.51.0 through `database/sql`, prepared statements, `mode=ro`, 256 MiB cache,
  no mmap, one connection.
- Round 1: KitDB without `.analytics` (KROW only). Round 2: KCOL built (33 s, 2,243,294,444 bytes, 1,683 chunks).
  Round 3: SQLite on a separate copy with an index on `(category, price)` (34 s, 220 MB).
  Every query returned the same result on both engines in every round.
- Clock: Go's Windows clock steps in about 0.5 ms. Point and page figures divide one timing over 2,000 or 500
  queries and are unaffected; a single analytic timing at or below 0.5 ms only means "within one clock step".

## Results

| Query | KitDB KROW | KitDB KCOL | SQLite | SQLite + index |
|---|---:|---:|---:|---:|
| One full row by key, 2,000 keys, second pass | 0.21 ms | 0.20 ms | 0.02 ms | 0.02 ms |
| Page of 20 rows in one merchant, 500 times | 0.64 ms | 0.54 ms | 0.21–0.38 ms | 0.18 ms |
| Count in one merchant by key | 81 ms | 78 ms | 11 ms | 11 ms |
| `COUNT(*)` whole table | 0 (catalog) | 0 (catalog) | 145–157 ms | 2.3 ms |
| Common category + SUM/AVG | 22.3 s | 0.44 s | 18.7–21.5 s | 0.23 s |
| Rare category + SUM/AVG/MAX | 19.9 s | 0.54 s | 18.9–19.9 s | ≤ 0.5 ms |
| High id range + SUM/AVG | 23.1 s | 0.22 s | 3.6–4.1 s | 3.8 s |
| GROUP BY category, 5,699 groups | 23.5 s | 0.81 s | 27.4–30.2 s | 1.28 s |
| GROUP BY merchant, count only | 2.5 s | 2.2 s | 1.0 s | 1.0 s |
| GROUP BY merchant + SUM(price) | 132 s | 132 s, then 0.66 s | 28 s | 29 s |

KCOL takes numeric and boolean fields by default; text joins only when declared analytical. The copied file
did not declare `merchant`, so rounds 1–2 grouped it by a sequential scan. After
`ALTER TABLE shopping ALTER COLUMN merchant SET ANALYTICS` and a 36 s refresh (`.analytics` grew by 54 MiB to
2,299,323,196 bytes) the same query took 0.66–0.69 s on the `kcol-batch` path, matching the 0.633 s of
`dbcompare/TEXT_ANALYTICS_13M_2026-09-04.md`. The count-only form still chose `index-only-group` (2.2 s).

## Reading

- Row work belongs to SQLite: about 10x on a point read, 2–3x on a page, 7x on a keyed count.
- Without extra structures both engines scan about 30 GB per analytic query; SQLite wins the id range and the
  merchant grouping.
- KCOL is KitDB's real contribution: 20–45x plain SQLite on filtered and grouped aggregates, for about 8% of the
  row file.
- One SQLite index beats KCOL on the exact query it serves (rare category within one 0.5 ms clock step) and helps nothing else (id
  range stays 3.8 s). Choosing between an index and KCOL per query is the adapter's job.

## Decimal as TEXT

`kitdbsqlite decimal` on an in-memory STRICT table: a TEXT column compares as text (`> 4.5` misses `10`),
orders as text (`10` before `4.5`), and `SUM` over it returns a REAL. INTEGER scaled by 10^scale does all three
exactly. On `main.db`, `rating` holds up to 16 fractional digits within 0–5 and `commission` is 0 on every row
(full scan, 23 s), so both fit a scaled int64.

Under the 27/10 rule of `KITWORK_DATABASE.md` mục 1 (a decimal keeps at most 15 digits, so a JavaScript number
holds every value), `rating` no longer fits a decimal and imports as `float()`.

## Key layout

`kitdbsqlite idlayout <directory> 5000000`: what a table's key costs on SQLite, for `KITWORK_DATABASE.md` mục 8.3.
Four narrow columns plus the key, an index on `userId` (every foreign key has one), 500,000 users, 16 KiB pages,
WAL, synchronous NORMAL, 10,000 rows a transaction, a 256 MiB cache smaller than every file. One run.

| Key | Insert rows/s | File MB | By key µs | By userId µs |
|---|---|---|---|---|
| `id()`, INTEGER PRIMARY KEY (rowid) | 37,399 | 326.0 | 7.10 | 30.10 |
| `uuid()` v7 BLOB, rowid table | 33,730 | 549.0 | 15.48 | 49.58 |
| `uuid()` v7 BLOB, WITHOUT ROWID | 26,110 | 499.7 | 10.75 | 61.73 |
| UUID v4 random BLOB, WITHOUT ROWID | 14,242 | 497.2 | 10.96 | 68.14 |

- `uuid()` against `id()`: 1.7x the file, 2.2x a lookup by key, 1.6x a lookup through the foreign key.
- Rowid table against WITHOUT ROWID for `uuid()`: inserts 29% faster and foreign-key lookups 20% faster, for
  key lookups 44% slower and a 10% larger file. The engine puts `uuid()` on a rowid table.
- A random v4 key inserts 1.8x slower than v7 in the same layout: each new key lands on any page instead of the
  right edge of the tree. Hence `uuid()` is v7.
- At 1,000,000 rows every file fits the cache: inserts 88,383 / 57,876 / 34,676 / 27,429 rows/s, files 64.0 / 108.7
  / 99.4 / 99.1 MB, in the order of the table.

## Reproduce

```bash
go build -o kitdbsqlite.exe ./benchmarks/kitdbsqlite
./kitdbsqlite.exe copy <copy of data.kitdb> main.db
./kitdbsqlite.exe verify main.db
./kitdbsqlite.exe bench <copy of data.kitdb> main.db "round 1"
./kitdbsqlite.exe refresh <copy of data.kitdb>
./kitdbsqlite.exe execute <copy of data.kitdb> "ALTER TABLE shopping ALTER COLUMN merchant SET ANALYTICS"
./kitdbsqlite.exe idlayout <scratch directory> 5000000
```
